# تدقيق مطابقة تكامل Meta لصندوق البريد الموحد

**تاريخ المراجعة:** 17 أغسطس 2026  
**النطاق:** Messenger وInstagram Professional وتعليقات Facebook Pages، مع الخادم وقاعدة البيانات والإعدادات المنشورة.  
**المنهجية:** مراجعة الكود، قراءة مخطط قاعدة البيانات والفهارس الفعلية، فحص HTTP آمن للنقطة المنشورة، ومقارنة بالوثائق الرسمية الحالية.

> تطلب Meta نقطة HTTPS تتحقق من طلب `GET` عبر `hub.verify_token` وتعيد `hub.challenge`، كما تتوقع استجابة `200 OK` خلال خمس ثوانٍ أو أقل للإشعارات. [1]

## النتيجة التنفيذية

**طبقة الاستقبال والتخزين مطبقة بدرجة جيدة، لكن الربط الحي لا يزال غير مهيأ ولا يمكن اعتباره متصلاً بـ Meta بعد.** الخادم المنشور متاح عبر HTTPS، وقاعدة البيانات تحتوي على الجداول والفهرس الفريد المطلوبين، إلا أن جدول إعدادات Meta لا يحوي أي سجل مفعل، ولا توجد حسابات Meta أو أحداث واردة. لذلك يعيد المسار المنشور حالياً `503` بصورة سليمة وآمنة بدلاً من قبول أحداث لا يملك مفاتيح التحقق الخاصة بها.

| محور المراجعة | النتيجة | الدليل التنفيذي |
|---|---|---|
| التحقق عبر GET | **مطابق** | المسار يقبل `hub.mode=subscribe` فقط، يقارن Verify Token، ثم يعيد `hub.challenge`؛ ويعيد `403` عند عدم التطابق. |
| توقيع POST | **مطابق** | استخدام HMAC-SHA256 على `req.rawBody` ومقارنة ثابتة الزمن لـ `X-Hub-Signature-256`. |
| زمن الإقرار | **مطابق** | يعيد `200 EVENT_RECEIVED` قبل بدء التطبيع والتخزين؛ وهذا يفي بشرط الاستجابة السريعة. [1] |
| رسائل Messenger | **مطابق للنطاق الأساسي** | يدعم `sender` و`recipient` و`timestamp` و`mid` والنص والرد المرجعي وأول مرفق. |
| Instagram وFacebook Comments | **مطابق للنطاق الأساسي** | يدعم `comments` في Instagram و`feed`/`item=comment` في Facebook، مع المعرفات والكاتب والوسيط والتعليق الأب. [2] [3] |
| منع تكرار التسليم | **مطابق** | جدول `social_inbox_webhook_events` يتضمن `UNIQUE(eventKey)`، مع اختبار مباشر لمسار duplicate. |
| سرية بيانات الربط | **مطابق** | App Secret وVerify Token وPage Access Token تخزن بـ AES-256-GCM ولا تعاد من راوتر الحالة إلى الواجهة. |
| الربط الحي مع Meta | **غير مهيأ** | لا توجد إعدادات أو حسابات أو أحداث Meta في قاعدة البيانات، والنقطة المنشورة أعادت `503` عند فحص آمن. |

## ما تم التحقق منه في الخادم

يُسجّل المسار `/api/webhooks/meta-social-inbox` بعد محلل JSON الذي يحتفظ بالبايتات الأصلية في `req.rawBody`. وهذا مهم لأن Meta تحسب التوقيع من الحمولة المرسلة، لا من كائن JSON بعد إعادة تسلسله. كما أن المقارنة تستخدم `timingSafeEqual` بعد التحقق من طول التوقيع، وهو أسلوب سليم لمنع المقارنة الزمنية البسيطة. [1] [2]

بعد نجاح التوقيع، يعيد الخادم `200 EVENT_RECEIVED` ثم يعالج الدفعة في مسار غير متزامن باستخدام `Promise.allSettled`. ويتعامل مع فشل كل حدث في السجل دون أن يمنع بقية أحداث الدفعة. يتوافق ذلك مع ضرورة الإقرار السريع؛ إلا أن الاعتمادية القصوى عند انقطاع العملية فوراً بعد الإقرار تحتاج صف مهام دائم، وهي توصية تحسين لا خلل في التحقق الحالي.

يدعم المطبع (`normalizer`) البنية العليا `object` و`entry[]` ويعالج الدفعات. تؤكد وثائق Instagram أن الإشعارات قد تجمع حتى 1000 تحديث في دفعة واحدة، وأن المحتوى التاريخي لا يمكن استعادته من Meta؛ لذلك من الصحيح حفظ الحمولة للأغراض التدقيقية. [2]

## ما تم التحقق منه في قاعدة البيانات

| العنصر | الحالة الفعلية | التقييم |
|---|---|---|
| `meta_integration_settings` | موجود، لكن عدد السجلات **0** | التصميم صحيح، الربط لم يبدأ فعلياً. |
| `social_inbox_webhook_events` | موجود، وعدد الأحداث **0** | فهرس `socialInboxWebhookEvents_eventKey_unique` موجود بالفعل. |
| حسابات Messenger/Instagram/Facebook | عددها **0** | ستنشأ تلقائياً عند حفظ Page ID وInstagram Account ID من صفحة الربط. |
| الحقول المشفرة | `appSecretEncrypted` و`verifyTokenEncrypted` و`pageAccessTokenEncrypted` موجودة | مطابقة لمتطلبات حماية الأسرار. |
| حالة التفعيل | لا يوجد صف مفعل | يفسر استجابة `503` الصحيحة من المسار المنشور. |

## فجوات متبقية قبل اعتبار الربط حياً

لا توجد فجوة تمنع بناء المشروع أو عمل استقبال Webhook بعد حفظ الإعدادات، لكن توجد متطلبات خارجية في Meta لا يمكن للكود تنفيذها من دون بيانات الحساب وتفويض التطبيق. يجب على المسؤول إدخال القيم من صفحة **ربط Meta** ثم إتمام تثبيت التطبيق والاشتراك في الحقول عبر لوحة Meta أو Graph API.

| الأولوية | الفجوة أو الإجراء | الأثر المطلوب |
|---|---|---|
| عالية | إدخال App ID وPage ID وInstagram Professional ID وApp Secret وVerify Token وPage Access Token، ثم تفعيل الربط | يخرج المسار من حالة `503` ويصبح جاهزاً للتحقق. |
| عالية | تثبيت التطبيق على صفحة Facebook والاشتراك في `feed` و`messages` عبر `/{page-id}/subscribed_apps` | Meta لن ترسل تعليقات أو رسائل إلى الخادم قبل هذه الخطوة. [3] |
| عالية | جعل تطبيق Meta في حالة **Live** وطلب الوصول/المراجعة المناسبين | Instagram يتطلب Live وAdvanced Access لاستخدام العملاء خارج أدوار التطبيق، وخاصة التعليقات. [2] |
| متوسطة | إضافة زر إداري ينفذ فحص/اشتراك `subscribed_apps` تلقائياً | يقلل أخطاء الإعداد اليدوي ويثبت حالة الاشتراك من داخل SGH. |
| متوسطة | تحويل `rawPayload` من `TEXT` إلى `MEDIUMTEXT` أو تخزين الحمولة في S3 | يحسن تحمّل دفعات Instagram الكبيرة؛ توثق Meta دفعات قد تصل إلى 1000 تحديث. [2] |
| متوسطة | إضافة قيد فريد للمحادثة على `(accountId, platform, channelType, externalThreadId)` | يمنع إنشاء سلسلتين لنفس المحادثة عند وصول أحداث مختلفة ومتزامنة قبل استكمال أول عملية إدخال. |
| منخفضة | تخزين جميع المرفقات في جدول فرعي بدلاً من أول رابط فقط | يوسع التعامل مع الرسائل التي تضم عدة مرفقات، في حين يدعم التنفيذ الحالي أول مرفق مع الاحتفاظ بالحمولة الخام. [4] |

## اختبار نقطة الإنتاج

تم طلب رابط الإنتاج عبر HTTPS مع Challenge تجريبي غير حساس. كانت الاستجابة `HTTP/2 503`، وهي النتيجة المتوقعة من الخادم عند عدم وجود إعدادات Meta مفعلة. لا يمكن، ولا ينبغي، اختبار Challenge صحيح أو توقيع POST حقيقي من دون إدخال Verify Token وApp Secret في صفحة الربط. بعد الإدخال، يجب تنفيذ اختبار Meta Dashboard الرسمي ثم إرسال رسالة وتعليق تجريبيين للتحقق من ظهور صفوف `processed` في سجل الأحداث.
