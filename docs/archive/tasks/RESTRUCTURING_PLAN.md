# خطة إعادة هيكلة لوحة تحكم الإدارة

## الهدف العام

إعادة لوحة تحكم الإدارة إلى النموذج الهجين المتفق عليه:

- إعادة الشريط الجانبي السابق بدل شريط التنقل العلوي الإداري.
- فصل شريط التبويبات المفتوحة في مكوّن مستقل.
- تثبيت الـ layout العام أثناء التنقل بين صفحات الإدارة.
- حفظ حالة التبويبات المفتوحة ومنع تكرارها أو فقدانها.
- منع إعادة بناء الشريط الجانبي والتبويبات بالكامل عند تغيير الصفحة.
- الحفاظ على الصلاحيات، وFeature Gating، والتنقل الحالي، وسلوك الهاتف.

## النطاق المتفق عليه

يشمل العمل مكونات لوحة الإدارة ومسار التنقل الداخلي فيها، ولا يشمل إعادة تصميم صفحات المحتوى نفسها أو تغيير الصلاحيات أو مخطط قاعدة البيانات إلا إذا ظهر احتياج تقني مباشر وموافق عليه.

## النموذج المعماري المستهدف

طبقة ثابتة:

- `DashboardShell` أو layout إداري ثابت.
- الشريط الجانبي الإداري.
- شريط التبويبات المفتوحة.
- حاوية المحتوى.

طبقة متحركة:

- صفحة الإدارة الحالية فقط داخل منطقة المحتوى.
- يتغير المسار والمحتوى دون إزالة الشريط الجانبي أو شريط التبويبات من شجرة React.

## مراحل المشروع الرئيسية

### المرحلة 1: فحص وتصنيف القوالب الحالية

المهام:

1. تمييز مكونات الـ layout الحالية:
   - الـ shell الرئيسي.
   - الشريط الجانبي السابق.
   - شريط التبويبات الحالي.
   - منطقة المحتوى.
   - مسار التوجيه الإداري.
2. تحديد أي مكونات تعتمد على المسار مباشرة.
3. تحديد المكونات التي يعاد تركيبها عند الانتقال بين صفحات الإدارة.
4. كتابة خريطة دقيقة لشجرة العرض الحالية وشجرة العرض المستهدفة.
5. تحديد نقاط التكامل مع الصلاحيات والميزات والإشعارات والتخزين المحلي.

مخرجات المرحلة:

- تقرير محلي عن البنية الحالية.
- تحديد المكونات التي ستبقى ثابتة.
- تحديد المكونات التي ستتغير داخل منطقة المحتوى فقط.
- خطة تنفيذ تفصيلية للمرحلة الثانية.

### المرحلة 2: فصل الـ layout الثابت عن routes

المهام:

1. إنشاء أو تعديل مكون layout إداري أساسي يحتوي على:
   - الشريط الجانبي.
   - شريط التبويبات.
   - منطقة المحتوى.
2. نقل مسؤولية عرض الصفحات إلى route داخلي واحد داخل منطقة المحتوى.
3. إخراج الشريط الجانبي والتبويبات من أغلفة routes المتكررة.
4. منع إعادة إنشاء الـ shell عند كل تغيير مسار.
5. الحفاظ على حالات التحميل والمصادقة وعدم الوصول.
6. التأكد من عدم كسر المسارات الحالية أو التحميل الكسول للصفحات.

مخرجات المرحلة:

- shell ثابت أثناء التنقل.
- تبديل المحتوى فقط داخل المساحة المخصصة.
- عدم إعادة تركيب الشريط الجانبي والتبويبات عند الانتقال بين الصفحات.

### المرحلة 3: إرجاع الشريط الجانبي السابق

المهام:

1. إزالة استخدام `AdminTopNavigation` من shell الإداري.
2. إعادة استخدام `DashboardSidebarV2` ومكوناته التابعة الحالية عند ملاءمتها.
3. الحفاظ على دعم:
   - الصلاحيات.
   - الميزات المرخصة.
   - الشارات والإشعارات.
   - الأدوات الكاملة والبحث.
   - تخصيص العناصر الظاهرة.
   - تجربة الهاتف.
4. استخدام مصدر التنقل المركزي الحالي دون إنشاء سجل روابط موازٍ.
5. ضبط active state ليعمل مع المسارات المباشرة والمسارات المتفرعة.
6. التأكد من أن الانتقال لا يستخدم تحميلًا كاملًا للمتصفح.

مخرجات المرحلة:

- عودة الشريط الجانبي السابق.
- بقاء الروابط والصلاحيات والسلوك الحالي.
- اختفاء شريط التنقل العلوي الإداري.

### المرحلة 4: فصل شريط التبويبات كـ component مستقل

المهام:

1. تثبيت `AdminTabs` كمكوّن مستقل مسؤول عن العرض والتفاعل البصري فقط.
2. نقل حالة التبويبات إلى مستوى layout الثابت.
3. إبقاء نموذج التبويب وعمليات الفتح والإغلاق في hook مركزي واضح.
4. منع تكرار التبويب عند فتح المسار نفسه.
5. الحفاظ على ترتيب التبويبات المفتوحة.
6. حماية تبويب الصفحة الرئيسية من الإغلاق إذا كان ذلك ضمن السلوك المتفق عليه.
7. تنفيذ fallback واضح عند إغلاق التبويب النشط.
8. الحفاظ على استعادة التبويبات من `localStorage` مع تصفية العناصر غير المتاحة.
9. منع إعادة بناء قائمة التبويبات عند كل إعادة render غير مؤثرة.
10. جعل النقر على التبويب يغير منطقة المحتوى فقط.

مخرجات المرحلة:

- شريط تبويبات مستقل.
- تبويبات مفتوحة ثابتة أثناء التنقل.
- عدم تكرار التبويبات.
- عدم فقدان الحالة عند تبديل التبويبات أو إعادة فتح الصفحة وفق السلوك المدعوم.

### المرحلة 5: التحقق السلوكي

المهام:

1. فتح صفحة من الشريط الجانبي.
2. الانتقال إلى صفحة ثانية.
3. التأكد أن الشريط الجانبي ثابت ولا يعاد تركيبه.
4. التأكد أن التبويبات السابقة بقيت مفتوحة.
5. التأكد أن التبويب النشط يتغير فقط عند اختيار تبويب.
6. التأكد أن منطقة المحتوى فقط هي التي تتغير.
7. اختبار إغلاق التبويب النشط.
8. اختبار إغلاق تبويب غير نشط.
9. اختبار fallback بعد الإغلاق.
10. اختبار منع التكرار.
11. اختبار استعادة التبويبات من التخزين المحلي.
12. اختبار الصلاحيات والميزات وحالات عدم الوصول.
13. اختبار العرض على سطح المكتب والهاتف.
14. تشغيل TypeScript وESLint والاختبارات ذات الصلة ثم الاختبارات العامة حسب الحاجة.

مخرجات المرحلة:

- تقرير تحقق سلوكي وتقني.
- توثيق أي فجوات متبقية.
- تأكيد جاهزية البنية أو تحديد أعمال إضافية.

## تعليمات التنفيذ والالتزام

1. لا نعيد إدخال شريط التنقل العلوي الإداري؛ نستخدم الشريط الجانبي فقط مع التبويبات المستقلة.
2. لا نربط حالة التبويبات بصفحة محددة؛ تكون الحالة في مستوى layout الأب الثابت.
3. لا نستخدم تحميلًا كاملًا للمتصفح عند التنقل الداخلي؛ يستخدم التنقل الداخلي في `wouter`.
4. لا نكرر أغلفة الـ shell حول routes الإدارية.
5. shell ثابت، ومنطقة المحتوى فقط هي التي تتغير.
6. كل صفحة إدارة تبقى داخل content region موحد.
7. نستخدم تحديثات الحالة الوظيفية مثل `setState(previous => next)` عند تعديل الحالة المتراكمة.
8. لا نغير واجهات عامة أو مصادر بيانات قائمة إلا عند الضرورة وبمراجعة أثر واضحة.
9. نستخدم مصدر التنقل المركزي الحالي، ولا ننشئ سجل روابط موازياً.
10. نحافظ على الصلاحيات وFeature Gating وعدم إظهار روابط غير مصرح بها.
11. نحتفظ بـ `localStorage` لاستعادة الحالة، مع التعامل الآمن مع البيانات غير الصالحة أو القديمة.
12. نضيف اختبارات سلوكية حقيقية للسلوك المتأثر، وليس اختبارات تعتمد فقط على mock assertions.
13. نلتزم بـ Clean Code وتقليل المسؤوليات داخل المكونات.
14. نضيف التوثيق والتعليقات فقط عند الحاجة لتفسير قرار أو سلوك غير بديهي.
15. نحافظ على أسماء الملفات والمكونات المتوافقة مع بنية المشروع ونمنع إعادة التسمية غير الضرورية.
16. بعد كل تعديل جوهري نشغل أقرب اختبار أو فحص قابل للتنفيذ قبل الانتقال.
17. لا ننتقل بين المراحل دون موافقة كتابية صريحة من المستخدم.
18. في نهاية كل مرحلة نراجع الكود مقابل خطة المرحلة ونذكر أي اختلاف.
19. يتم إنشاء commit محلي بوصف دقيق بعد اجتياز فحوصات المرحلة، ولا يتم دفعه إلى remote إلا بطلب صريح.
20. لا يتم تعديل أو حذف تغييرات غير مرتبطة بالعمل الحالي.

## منهجية Phase-Gate الإلزامية

لكل مرحلة رئيسية، وبالترتيب الحرفي:

### 1. الفحص والتحليل (Audit & Analysis)

يبدأ العمل بفحص كل ملف وسطر كود له علاقة مباشرة بالمرحلة الحالية، وتحليل تدفق البيانات والعرض، وتحديد أفضل طريقة برمجية متوافقة مع النظام الحالي والمراحل اللاحقة.

### 2. التخطيط الدقيق والمعايير (Granular Planning & Standards)

يتم إنشاء خطة تنفيذ دقيقة للمرحلة الحالية فقط، مقسمة إلى مهام صغيرة، مع تحديد الملفات، والمسؤوليات، ومعايير Clean Code، والتوثيق، والاختبارات، ومعايير القبول.

### 3. التوقف للمراجعة والاعتماد (Hold for Approval)

يتوقف العمل تمامًا بعد تقديم الخطة. لا تتم كتابة أو تعديل كود التطبيق قبل موافقة المستخدم الصريحة.

### 4. التنفيذ والمراجعة ثم الحفظ والملخص (Implementation, Commit & Summary)

بعد الموافقة، يتم تنفيذ المهام، ومراجعة الكود ومطابقته مع الخطة، وتشغيل الفحوصات، ثم إنشاء commit محلي دقيق، وتقديم ملخص واضح، وطلب الإذن للمرحلة التالية.

### 5. الانتقال للمرحلة التالية

لا تبدأ المرحلة التالية إلا بعد موافقة المستخدم. وتكرر لها الخطوات الأربع السابقة بنفس الترتيب.

## معايير قبول النتيجة النهائية

- الشريط الجانبي ثابت أثناء التنقل بين صفحات الإدارة.
- شريط التبويبات مستقل وثابت.
- تغيير الصفحة لا يؤدي إلى تحميل كامل للمتصفح.
- تبديل التبويبات لا يعيد تهيئة shell أو التبويبات بالكامل.
- لا توجد تبويبات مكررة للمسار نفسه.
- إغلاق التبويب يعيد المستخدم إلى تبويب صالح بطريقة متوقعة.
- الصلاحيات والميزات تمنع الوصول غير المصرح به.
- سلوك الهاتف وسطح المكتب يعملان دون تداخل.
- TypeScript وESLint والاختبارات ذات الصلة ناجحة.
- كل مرحلة موثقة ومحفوظة في commit مستقل.
