# جرد فرص ربط الإشعارات الموحدة

**النطاق:** وحدات التشغيل والخدمات الخلفية في بوابة SGH CRM.  
**الهدف:** تحديد الأحداث التي تستحق إشعاراً داخل مركز الإشعارات، مع ترتيب التنفيذ دون إنشاء بيانات تجريبية أو تغيير تدفقات العمل الحالية.

## الخلاصة التنفيذية

نظام الإشعارات الموحد يغطي حالياً دورة موافقات المحتوى، التسجيلات الجديدة للمواعيد والمخيمات والعروض، وتغيّر حالة هذه التسجيلات، إضافةً إلى التفضيلات الشخصية، السياسة النظامية، الملخص اليومي، وسجل التدقيق. إلا أن **معظم التدفقات اليومية عالية القيمة لا تزال خارج المركز الموحد**: المهام، العملاء المحتملون، صندوقا WhatsApp والبريد الاجتماعي، التعيينات، وحالات فشل التكاملات والعمليات الخلفية.

> الأولوية ليست لإرسال مزيد من التنبيهات، بل لإيصال الحدث إلى **الشخص المسؤول** في الوقت المناسب، ضمن تفضيلاته، ومن دون تضمين بيانات طبية أو شخصية حساسة في عنوان الإشعار أو معاينته.

## ما هو مرتبط حالياً

| المجال | التغطية الحالية | الدليل في المشروع | الملاحظة |
|---|---|---|---|
| موافقات المحتوى | طلب المراجعة والاعتماد والرفض | `server/routers/content/approvals.ts` و`server/_core/notificationHelper.ts` | جيد؛ يبقى إشعار تعيين المراجع ناقصاً. |
| التسجيلات الجديدة | إنشاء موعد/تسجيل مخيم/طلب عرض | راوترات `appointments/routes/submitRoute.ts` و`campRegistrations/registration.ts` و`offerLeads/registration.ts` | يخضع للسياسة والتفضيلات الموحدة. |
| تغيّر الحالات | مواعيد ومخيمات وعروض | `notificationFollowUpService.ts` مع راوترات الحالة | يغطي التنبيهات التشغيلية للمتابعين. |
| إعدادات الإشعار | المستخدم والنظام والملخص | `server/routers/notifications.ts` | محفوظة مع سجل تدقيق. |
| المحتوى المجدول | فشل بوابة الجودة قبل النشر | مسار CMS المجدول وإشعارات المحتوى | يحتاج مراجعة موحدة لاحقة لمستوى التفاصيل فقط. |

## فجوات ربط عالية الأولوية

| الأولوية | الحدث المقترح | المستلم المقترح | المصدر/النوع المقترح | سبب الأولوية |
|---|---|---|---|---|
| **P0** | رسالة WhatsApp واردة جديدة أو محادثة معلَّمة مهمة | المعيَّن للمحادثة، ثم فريق الاستقبال عند عدم التعيين | `whatsapp` / `message_received` | يمنع تأخر الرد على المرضى والعملاء. |
| **P0** | تعيين أو إعادة تعيين محادثة WhatsApp | المستخدم المعيَّن | `whatsapp` / `conversation_assigned` | يربط الملكية بالمسؤول الفعلي. |
| **P0** | رسالة أو تعليق وارد في صندوق البريد الاجتماعي | المعيَّن، أو الدور المسؤول عن القناة | `social_inbox` / `message_received` أو `comment_received` | صندوق البريد الموحد يحفظ الأحداث لكنه لا ينبه المالك. |
| **P0** | طلب متابعة أو تعيين مسؤول لتعليق | المستخدم المعيَّن وفريق الإشراف عند التصعيد | `social_inbox` / `follow_up_assigned` | موجود في `updateCommentWorkflow` بلا إشعار. |
| **P0** | إنشاء مهمة أو مهمة متابعة وتعيينها | المستخدم المعيَّن | `tasks` / `task_assigned` | راوترا `tasks.ts` و`followUpTasks.ts` لا يرسلان إشعارات. |
| **P0** | استحقاق مهمة أو تجاوز موعدها | المعيَّن، ثم المشرف عند تجاوز عتبة زمنية | `tasks` / `task_due` و`task_overdue` | يحتاج مهمة دورية آمنة مع منع التكرار. |
| **P0** | عميل محتمل جديد أو تغيّر مرحلته | الأدوار المسؤولة عن المبيعات/الاستقبال | `leads` / `lead_created` و`lead_status_changed` | ما زال المسار يعتمد على `notifyOwner` وTelegram والبريد خارج المركز الموحد. |
| **P0** | فشل/انقطاع/انتهاء تفويض تكامل رئيسي | مسؤولو التكاملات | `integrations` / `connection_error` أو `authorization_expiring` | توقف القناة قد يخفي الرسائل أو يفشل الإرسال. |

## فجوات متوسطة الأولوية

| المجال | الأحداث التي ينبغي ربطها | التنفيذ المقترح |
|---|---|---|
| الحملات | تعيين قائد الحملة، التفعيل أو الإيقاف، قرب تاريخ النهاية، تجاوز الميزانية أو عدم بلوغ الهدف | إضافة إشعار عند التحديث مع مهمة يومية للعتبات؛ لا تنبه عند كل تعديل وصفي. |
| موافقات المحتوى | تعيين مراجع جديد أو إعادة التعيين بعد الرفض | إرسال إشعار مباشر للمراجع المعيَّن من `assignReviewer`. |
| طلبات الوصول | تقديم طلب، قبول، رفض | إشعار للمُقدِّم وللمسؤولين؛ المسار الحالي ينبه المالك فقط عند القبول. |
| نتائج المختبر | نتيجة جاهزة، إخفاق نهائي بعد إعادة المحاولة، فشل إرسال WhatsApp | إشعار داخلي للمسؤول التشغيلي فقط، مع تجنب وضع أي نتيجة أو تشخيص في النص. |
| المواعيد | تغيير التاريخ أو الطبيب، إلغاء الموعد، فشل رسالة الترحيب أو التذكير | إشعار للفريق المسؤول؛ لا تكرر إشعار تغيير الحالة الموجود حالياً. |
| وسائط وCMS | اكتمال استيراد/تصدير، فشل معالجة ملف أو نشر وسائط | تلخيص العملية وإظهار رابط السجل بدلاً من تنبيه لكل ملف. |

## فجوات تشغيلية منخفضة الأولوية

ينصح بتجميع تنبيهات النسخ الاحتياطي، فشل الاستعادة، صحة الترخيص، فشل مزامنة القوالب، وفشل مهام التحويل/التحديث ضمن قناة **عمليات النظام**. ترسل فقط عند الفشل، أو عند عودة الخدمة بعد فشل سابق، ولا ترسل لكل سجل أخطاء منفرد لتفادي ضجيج التنبيهات.

## نقاط الدليل المهمة

| المجال | ما تم رصده | الأثر |
|---|---|---|
| المهام | `server/routers/tasks.ts` و`server/routers/followUpTasks.ts` ينفذان الإنشاء والتحديث والحذف والتعيين بلا سياسة إشعارات موحدة | فجوة مباشرة في تدفق العمل الفردي. |
| العملاء المحتملون | `server/routers/leads.ts` يستخدم تنبيه المالك والبريد وTelegram عند الإنشاء، مع سجل تدقيق عند تغيير الحالة | يحتاج ترحيل الحدث إلى خدمة السياسة مع الإبقاء على القنوات الخارجية اختيارية. |
| الصندوق الاجتماعي | `server/routers/socialInbox.ts` يحتوي التعيين، القراءة، طلب المتابعة، الرد والإخفاء، ولا يستدعي خدمة الإشعارات | مصدر رئيسي للأحداث التي تحتاج تعييناً واستجابة. |
| WhatsApp | `server/routers/whatsapp/conversations.ts` يدعم التعيين والأهمية والأرشفة؛ و`messages.ts` و`templates.ts` يدعمان الإرسال والمزامنة | يجب الربط عند الوارد والتعيين والإخفاق النهائي، لا عند كل رسالة صادرة عادية. |
| التكاملات | `integrationConnections.ts` وراوترات Meta تدير الاتصال والانقطاع وOAuth | يلزم إشعار إداري عند الفشل أو فقد الاتصال أو قرب انتهاء التفويض. |
| نتائج المختبر | `tasks/cron/labResultsPoller.ts` يعيد المحاولة ويحدد الفشل بعد ثلاث محاولات | يحتاج تنبيه تشغيل داخلي عند الفشل النهائي فقط. |

## تحديث التحقق بعد التنفيذ

لم يعثر فحص النسخة الحالية على راوتر أو نموذج بيانات لطلبات وصول تشغيلية. لذلك لم يُضف رابط إشعارات مصطنع لهذه الفئة؛ ويعاد فتح بندها فقط عند إضافة دورة فعلية لتقديم طلب الوصول وقبوله أو رفضه.

## متطلبات العقد قبل التنفيذ

تحتاج قائمة المصادر الحالية إلى توسيع مضبوط بدلاً من إعادة استخدام `system` أو `manual`. المصادر المقترحة هي: `tasks` و`leads` و`whatsapp` و`social_inbox` و`patients` و`access` و`operations`. كما يلزم إضافة أنواع محددة مثل `task_assigned` و`task_overdue` و`lead_created` و`message_received` و`conversation_assigned` و`comment_received` و`connection_error` و`job_failed`.

ينبغي أن تبقى خدمة `notifyEligibleRecipients` هي بوابة السياسة للأحداث الموجهة بالأدوار. أما التعيين الفردي فيحتاج مساراً موحداً يتأكد من تفضيلات المستخدم وملكية الحدث قبل إنشاء الإشعار. لكل حدث خارجي أو دوري، يلزم مفتاح تكرار في السياق لمنع إنتاج عدة إشعارات للحادثة نفسها.

## تسلسل التنفيذ المقترح

1. **حزمة الاستجابة P0:** ربط التعيين والوارد في WhatsApp وصندوق البريد الاجتماعي، ثم المهام ومهام المتابعة، مع مصادر وأنواع جديدة واختبارات سياسة المستلم.
2. **حزمة العملاء والتكاملات P0:** ترحيل العملاء المحتملين من تنبيه المالك إلى المركز الموحد، وإضافة تنبيه فشل/انقطاع التكاملات مع تهدئة التكرار.
3. **حزمة عمليات P1:** إنذارات الاستحقاق والتأخر للمهام، وإخفاق نهائي لمهام المختبر والنسخ الاحتياطي، باستخدام Heartbeat ومسارات محمية ومفاتيح تكرار.
4. **حزمة الحملات والمحتوى P1:** تعيين قائد الحملة/المراجع، عتبات الميزانية والمواعيد، ونتائج الاستيراد والتصدير.

## ضوابط الجودة والخصوصية

لا ينبغي أن تتضمن معاينات الإشعارات تشخيصاً أو نتيجة مختبر أو رقم هوية أو تفاصيل سريرية. يقتصر الإشعار على وصف عملي واسم المجال، ويوجه المستخدم إلى صفحة محمية. كما يجب أن تكون التنبيهات من نوع fire-and-forget بحيث لا تعطل إنشاء التسجيل أو الرسالة أو المهمة الأصلية، مع تسجيل الفشل في السجل التشغيلي.
