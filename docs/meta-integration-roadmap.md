# خارطة تكامل منظومة Meta مع بوابة SGH CRM

**تاريخ المراجعة:** 19 أغسطس 2026  
**إعداد:** Manus AI

## الخلاصة التنفيذية

لا يُقصد بربط Meta مجرد استقبال رسائل Facebook وInstagram. فالمنظومة المناسبة لبوابة SGH CRM تتكون من أربع طبقات مترابطة: **الأصول الاجتماعية والمحتوى**، و**المراسلة التجارية وWhatsApp**، و**العملاء المحتملون والإعلانات والقياس**، ثم **التفويض وإدارة الأصول**. يمكن للنظام أن يربط معظم هذه الطبقات، لكن الأولوية الصحيحة هي تأسيس التفويض الرسمي للأصول أولاً، ثم توصيل Lead Ads وWhatsApp، وبعد ذلك قياس التحويلات وإدارة الإعلانات.

> **قاعدة تشغيلية:** لا يُفعّل أي اتصال حي قبل أن يكون حساب Meta Business، والصفحة أو الحساب، والصلاحيات، والمراجعة المطلوبة، والتفويض الممنوح من مالك الأصل مكتملة. لا يكفي حفظ Client ID وClient Secret وحدهما.

| Business Management وFacebook Login for Business | إدارة الأصول التجارية والتفويض، وحسابات النظام، وربط التطبيقات بالصفحات والحسابات الإعلانية. | أساس صفحة «إعدادات الربط العامة»، OAuth المنظم، تخزين التوكنات المشفرة، ودعم عدة فروع أو أصول. | **أساسي** |
| Threads API | إنشاء منشورات أحادية أو Carousel، استرجاع الوسائط والملفات الشخصية، إدارة الردود، الحذف، Insights وWebhooks. [8] | إضافة Threads كوجهة نشر وصندوق تفاعل وتقارير؛ مناسب كمرحلة توسع بعد استقرار Facebook وInstagram. | **متوسط** |

| منتجات غير مناسبة حالياً | Horizon وWearables وخدمات المطورين غير المرتبطة مباشرة بالتشغيل التجاري للـ CRM. | لا تدخل في خارطة CRM الحالية إلا عند وجود حالة استخدام مستقلة وواضحة. | **خارج الأولوية** |

## ما هو موجود داخل المشروع الآن

أظهرت مراجعة المشروع أن البوابة لا تبدأ من الصفر. توجد طبقة Meta Social Webhook تتحقق من التوقيع وتعالج رسائل Messenger وInstagram وتعليقات Facebook وInstagram، كما توجد واجهة صندوق بريد موحد ومساحة عمل لسياقات التعليقات وإجراءات الرد والإخفاء والرسالة الخاصة. كذلك توجد صفحة نشر متعددة المنصات وإعدادات Meta مشفرة، ومهمة Heartbeat منشورة للنشر المجدول.

| القدرة | الحالة الحالية | ما يلزم للانتقال إلى تشغيل حي كامل |
|---|---|---|
| Webhook الاجتماعي لـ Meta | **منفذ** | إدخال بيانات التطبيق الحية، إكمال App Review والصلاحيات، الاشتراك بالأصول الحقيقية، ثم اختبار الرسائل والتعليقات الحية. |
| صندوق وارد Messenger وInstagram وتعليقات Facebook/Instagram | **منفذ** | OAuth لحسابات الأعمال، Page/IG tokens صحيحة، وسياسة تشغيل للردود البشرية والآلية. |
| إجراءات التعليقات الرسمية | **منفذ جزئياً** | تحقق حي من الصلاحيات والتوكنات، وسجل تدقيق لمشرفي المحتوى والإجراءات الحساسة. |
| النشر إلى Facebook وInstagram | **واجهة وسير عمل جاهزان** | موصلات OAuth والنشر الفعلية وحسابات `social_publish_accounts` المصرح بها. |
| WhatsApp | **هيكل واسع موجود** | تدقيق الاعتمادات الحية، توحيد التسجيل المضمن أو الإعداد الحالي، Webhooks، القوالب والموافقات، وحدود إرسال الرسائل. |
| Pixel وConversions API للموقع | **موجودة كطبقة أولية** | نقل الاعتمادات إلى إعدادات آمنة، مراجعة نسخة Graph API عند التفعيل، Deduplication بين Pixel وCAPI، Events Manager واختبارات الجودة. |
| قياس إعلانات وLead Ads | **غير مكتمل** | Leadgen Webhook، استرجاع بيانات النموذج، تطبيع الحقول، نسب المصدر، وواجهة تقارير تسويقية. |
| Marketing API | **غير منفذ** | اتصال حساب الإعلان، صلاحيات ومراجعات مطلوبة، طبقة تقارير ثم إدارة حملات تدريجية. |
| Threads | **غير منفذ** | صفحة إعدادات وربط OAuth ووجهة نشر/تفاعل اختيارية. |

## خارطة التنفيذ المقترحة

تسلسل التنفيذ أدناه يقلل من مخاطر التفعيل ويركز على الحالات التي تحقق قيمة تشغيلية فورية للمستشفى دون جعل النظام يعتمد على بيانات تسويقية حساسة.

| المرحلة | النتيجة المطلوبة | المكونات العملية | معيار الاكتمال |
|---|---|---|---|
| 1. تأسيس التفويض والأصول | ربط موحد وآمن للأصول | Facebook Login for Business، حساب Business Manager، Page/IG/WABA/Ad Account، AES-256-GCM للتوكنات، تدوير وإبطال التوكنات، سجل تدقيق. | يمكن للمسؤول ربط أصل وإلغاء ربطه، ولا يظهر أي سر أو Access Token في الواجهة أو السجل. |
| 2. WhatsApp لخدمة المرضى | قناة محادثة رسمية قابلة للتشغيل | Cloud API، Webhooks، قوالب خدمة معتمدة، Inbox موحد، إسناد موظف، إلغاء الاشتراك والامتثال، وربما Embedded Signup. | رسالة واردة وصادرة وقالب معتمد وحالة التسليم تظهر في CRM مع سجل تدقيق. |
| 3. Lead Ads إلى CRM | صفر إدخال يدوي للعملاء المحتملين | Webhook `leadgen`، استرجاع تفاصيل النموذج، تطبيع وإزالة التكرار، مصدر الحملة والنموذج، قواعد إسناد ومتابعة. | وصول Lead تجريبي ينشئ سجلاً واحداً فقط ويُسند تلقائياً للفريق. |
| 4. قياس الحجوزات والتحويلات | تقارير جودة التسويق لا مجرد عدد الرسائل | Pixel مع CAPI، أحداث `Lead` و`Schedule` و`CompleteRegistration`، `event_id` موحد لمنع التكرار، Events Manager. | تظهر الأحداث في Events Manager ويمكن نسبها للحملة دون إرسال بيانات صحية. |
| 5. تقارير الإعلانات | ربط إنفاق الحملة بالنتائج | Marketing API وInsights، لوحات تكلفة Lead والحجز ومعدل التحويل، تنبيهات انخفاض الجودة. | تقرير يومي مطابق للأرقام الأساسية في Ads Manager ضمن هامش التحديث المتوقع. |
| 6. إدارة الإعلانات والجماهير | تحكم متدرج ومراجع | إنشاء ومراجعة الحملات، قواعد إعلانية، جماهير مسموحة وموافقات داخلية. | لا ينشر أي إعلان أو يغير ميزانية إلا عبر دور إداري وموافقة وسجل تدقيق. |
| 7. Threads وCatalog | توسع اختياري | Threads للنشر والإشراف، كتالوج للخدمات أو العروض غير السريرية عند الحاجة. | قيمة أعمال مؤكدة وسيناريو خدمة أو تسويق مصادق عليه قبل التفعيل. |

## متطلبات الوصول قبل التفعيل

يلزم توفير حساب Meta Business وتطبيق Meta مملوك للمؤسسة أو مفوض لها، ثم ربط الأصول المطلوبة بالحساب. تستخدم قدرات Lead Ads، مثلاً، Page Access Token من شخص لديه مهمة `ADVERTISE` على الصفحة، مع الصلاحيات التي توضحها Meta مثل `leads_retrieval` و`pages_manage_metadata` و`pages_show_list` و`pages_read_engagement` و`ads_management`. [5]

بالنسبة إلى WhatsApp، يمكن أن يعطي التسجيل المضمن بيانات الحساب والرقم والرمز المؤقت، لكن استبدال الرمز وتسجيل الرقم والاشتراك في Webhooks يجب أن تتم خادمياً؛ وفي الوضع الحي تظهر فقط الصلاحيات المعتمدة في App Review. [6] لذلك لا ينبغي الاكتفاء بإعدادات العميل الحالية عند بناء تدفق OAuth النهائي.

## ضوابط الخصوصية والأمان للرعاية الصحية

ينبغي أن تكون بيانات Meta التسويقية منفصلة منطقياً عن السجل الطبي. يُستخدم الاسم أو الهاتف أو البريد، عند وجود أساس قانوني وموافقة مناسبة، فقط بالقدر اللازم للقياس أو المطابقة التي تسمح بها السياسة؛ ولا يجب إرسال التشخيص أو نتائج الفحوصات أو الوصفات أو محتوى المحادثات الطبية أو أي حالة صحية ضمن أحداث التحويل أو الجماهير أو معلومات الإعلانات. كما يجب أن تخضع الرسائل التجارية وسياسات الموافقة والإلغاء والمحتوى الآلي لمراجعة الامتثال القانوني والسريري المحلية قبل التشغيل.

| الضابط | التطبيق المقترح |
|---|---|
| فصل البيانات | تخزين معرّفات Meta والتسويق في جداول منفصلة عن السجل الطبي، مع مراجع داخلية أدنى ما يلزم. |
| أقل صلاحية | منح Scope محدد لكل موصل وتقييد عمليات الربط والتشغيل على دور المسؤول. |
| تشفير الأسرار | تشفير التوكنات وClient Secret وتجنب تسجيلها في السجلات أو إعادتها للواجهة. |
| الموافقة | حقل قابل للتدقيق لموافقة الاتصال التسويقي وقناة الاتصال وتاريخ الإلغاء. |
| الإشراف البشري | إبقاء الردود المرتبطة بالحالة الطبية والمواعيد الاستثنائية تحت اعتماد موظف مخول. |
| قياس آمن | إرسال أسماء أحداث عامة مثل «موعد محجوز» دون سبب زيارة أو تخصص أو تفاصيل علاج. |

## القرار الموصى به للبدء

ابدأ بـ **مرحلة التفويض الموحد ثم WhatsApp وLead Ads**. هذا التسلسل يربط قناتين تحققان أثراً فورياً: استقبال عميل محتمل من إعلان Meta إلى CRM، ثم التواصل معه عبر قناة أعمال رسمية قابلة للتتبع. بعد ضبط هذا التدفق، يُضاف Conversions API لقياس الحجوزات، ثم Marketing API للتقارير. تأجيل التحكم المباشر في الحملات وThreads والكتالوجات يقلل المخاطر التشغيلية ولا يؤخر القيمة الأساسية.
