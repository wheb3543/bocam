# خطة نظام الإشعارات الموحد

## نتيجة التدقيق

يوجد راوتر ومركز إشعارات أوليان، لكن جدول `notifications` غير منشأ في قاعدة الإنتاج. كما أن واجهة الرأس تعرض قائمة مختصرة فقط، وزر الإشعارات في الشريط الجانبي غير مرتبط بوجهة، ومكوّن «طلبات قيد الانتظار» في لوحة الإدارة يعتمد على استعلامات حجوزات مستقلة ولا يمثل سجلاً موحداً للإشعارات.

## قرار التنفيذ

سيُستخدم جدول `notifications` كسجل لكل مستلم بدلاً من إنشاء بيانات تجريبية أو قناة خلفية منفصلة. ستبقى الإشعارات مرتبطة بالمستخدم المستلم، مع النوع والأولوية وحالة القراءة والإجراء المرتبط والبيانات الوصفية. سيقتصر إنشاء الإشعارات اليدوي أو الموجّه على الإجراء الإداري، بينما تظل إجراءات القراءة والحذف خاصة بالمستلم.

## نموذج البيانات

| الحقل | الغرض |
| --- | --- |
| `userId` | المستلم الفردي للإشعار. |
| `type` | تصنيف موحد للمحتوى والموافقات والحجوزات والتكاملات والنظام والخصوصية. |
| `priority` | منخفضة أو متوسطة أو عالية. |
| `isRead` و`readAt` | متابعة حالة القراءة. |
| `actionUrl` و`actionLabel` | انتقال آمن إلى سياق المعالجة. |
| `data` | بيانات وصفية JSON لا تُعرض مباشرةً للمستخدم. |
| `expiresAt` | تاريخ انتهاء اختياري للتنظيف الدوري الآمن لاحقاً. |

## تجربة الإدارة

سيبقى جرس الرأس للوصول السريع، ويقود زر الشريط الجانبي إلى صفحة `/admin/notifications`. ستعرض الصفحة بطاقات إحصائية، فلاتر النوع والأولوية وحالة القراءة، قائمة قابلة للقراءة، إجراءات تحديد المقروء وحذف المقروء، وزراً للانتقال إلى الإجراء المرتبط عند توفره. سيظهر العداد غير المقروء في الرأس والشريط الجانبي.

## مصادر الإطلاق الأولى

تُوحّد تنبيهات الموافقات والمحتوى الموجودة في مساعد الإشعارات الخادمي. ويُضاف عقد آمن لإشعارات الحجوزات والتكاملات والخصوصية لكي تربطها الخدمات اللاحقة دون تعديل الواجهة أو إنشاء بيانات مزيفة.
