# الخطة التنفيذية المرحلية لتحديث وتغطية وثائق المشروع

**الحالة:** مكتملة ومحققة بالكامل بنسبة 100% (المراحل 0–19 مغلقة ومعتمدة رسمياً)
**تاريخ إعداد الخطة:** 2026-09-11  
**تاريخ الإغلاق والتسليم النهائي:** 2026-09-13  
**المشروع:** BOCAM CRM  
**المنهجية:** Phase-Gate Methodology  
**المرجع الختامي الشامل:** [التقرير الختامي لحوكمة التوثيق والاستدامة والتسليم النهائي](./FINAL_DOCUMENTATION_GOVERNANCE_SUSTAINABILITY_REPORT.md)  
**قاعدة الانتقال:** لا تبدأ أي مرحلة تنفيذية ولا تنتقل إلى المرحلة التالية دون موافقة كتابية صريحة من صاحب المشروع.

## 1. الغرض من هذا المستند

هذا المستند هو المرجع الثابت لتنفيذ مشروع تحديث وثائق BOCAM CRM وربطها بالكود الفعلي. هدفه إنشاء توثيق:

- مطابق للسلوك الحالي في الكود والاختبارات.
- شامل للمجالات الوظيفية والتقنية والتشغيلية.
- منظم حسب المجال وقابل للتوسع.
- قابل للمراجعة والتدقيق والتحديث المستمر.
- خالٍ من الوثائق المتعارضة أو القديمة غير الموسومة.

لا يصرح هذا المستند بتعديل الكود أو نقل الملفات أو حذف الوثائق. هذه الخطة تصف العمل الذي سيُنفذ لاحقًا مرحلةً مرحلة.

## 2. نتائج الفحص الأولي

تمت مراجعة الهيكل العام للمشروع ومواقع الكود والاختبارات والوثائق. أهم الحقائق التي تتحكم في الخطة:

| العنصر | الوضع المرصود |
|---|---|
| واجهة المستخدم | `client/src/` وتضم صفحات عامة وإدارية وبوابة المريض ومكونات مشتركة |
| الخادم | `server/` ويضم الراوترات والخدمات وقاعدة البيانات والتكاملات والمهام المجدولة |
| الراوترات | مجالات للمصادقة، المواعيد، الحملات، المحتوى، المرضى، الصلاحيات، WhatsApp، Social Inbox، التقارير وغيرها |
| قاعدة البيانات | `drizzle/schema.ts` و`drizzle/relations.ts` وترحيلات عديدة وطبقة DB داخل `server/database/` |
| التكاملات | Meta، WhatsApp، Social Publishing، Social Inbox، التخزين، Redis، البريد، Telegram، OAuth |
| الاختبارات | اختبارات وحدة وتكامل في `client/` و`server/`، وستة مسارات E2E رئيسية في `e2e/` |
| التشغيل | Docker، النسخ الاحتياطي، المراقبة، Nginx، CI/CD، مهام cron |
| الوثائق | المركز الرئيسي `docs/` مع وثائق موزعة في الجذر و`deploy/` و`drizzle/` و`.devin/` و`.github/` |
| المشكلة الرئيسية | وجود وثائق متكررة أو قديمة وفهرس لا يعكس كل الملفات الحالية |

## 3. قواعد العمل الملزمة

### 3.1 قواعد المصدر المرجعي

عند وجود تعارض، يُسجل التعارض ولا يتم التخمين. ترتيب التحقق هو:

1. المتطلبات والسياسات المعتمدة من صاحب المشروع.
2. السلوك الفعلي للكود الحالي.
3. الاختبارات الحالية وسلوكها المتوقع.
4. مخطط قاعدة البيانات والترحيلات الفعلية.
5. الوثائق الحالية.
6. التعليقات والملاحظات القديمة.

### 3.2 قواعد النطاق

- كل مرحلة تغطي مجالًا محددًا أو طبقة مشتركة محددة.
- لا يتم تعديل الكود إلا إذا كان ذلك ضروريًا لتصحيح مثال أو اختبار توثيقي أو كشف تعارض، وبعد موافقة مستقلة إذا خرج عن نطاق التوثيق.
- لا يتم حذف وثيقة قديمة؛ تُوسم أو تُنقل إلى الأرشيف بعد تحديد بديلها.
- لا يتم دمج وثائق متشابهة قبل تحديد الوثيقة المرجعية والروابط الواردة إليها.
- لا يتم اعتبار التوثيق مكتملًا بمجرد وجود ملف؛ يجب إثبات مطابقته للكود والاختبارات.

### 3.3 الحالة الإلزامية لكل وثيقة

كل وثيقة يتم إنشاؤها أو تحديثها يجب أن تحمل بيانات وصفية أو قسمًا واضحًا يحدد:

| الحقل | القيم المقترحة |
|---|---|
| الحالة | `canonical`, `working`, `deprecated`, `archived`, `generated` |
| الجمهور | مستخدم، مسؤول، مطور، مشغل، فريق أمان |
| المجال | المجال الوظيفي أو التقني |
| المصدر | ملفات الكود والاختبارات والـ schema المرتبطة |
| آخر مراجعة | تاريخ ISO مثل `2026-09-11` |
| المالك | الفريق أو الشخص المسؤول |
| البديل | رابط الوثيقة المرجعية إن كانت الوثيقة قديمة |

### 3.4 معيار توثيق الكود

سيتم تطبيق Clean Code وKISS وDRY وSingle Responsibility وSeparation of Concerns دون إعادة تصميم غير مطلوبة. التعليقات تشرح السبب والقيود وقرارات التصميم فقط، ولا تكرر ما هو واضح من الكود. أمثلة الكود يجب أن تكون قابلة للتشغيل أو موسومة صراحة بأنها شبه كود.

## 7. بوابات الجودة العامة

لا تُغلق أي مرحلة إلا إذا تحققت جميع الشروط التالية بحسب نطاقها:

- تم فحص ملفات الكود والاختبارات والوثائق المرتبطة.
- تم تسجيل الملفات التي لم تُفحص وسبب استثنائها.
- كل ادعاء مهم في الوثيقة مرتبط بمصدر فعلي.
- تم توثيق الصلاحيات والأخطاء والحالات الحدية عند وجودها.
- لا توجد روابط محلية مكسورة في الملفات المعدلة.
- لا توجد أسرار أو بيانات شخصية أو أمثلة مضللة.
- تم تشغيل أصغر تحقق مناسب: lint أو typecheck أو اختبار أو link check.
- تمت مراجعة التغيير مقابل خطة المرحلة.
- حصلت المرحلة على موافقة المستخدم قبل بدء المرحلة التالية.

## 8. مصفوفة التغطية النهائية المطلوبة

يجب أن تتضمن المصفوفة صفًا لكل عنصر مهم في الكود، على الأقل:

| الطبقة | العنصر | المجال | الاختبار | الوثيقة | الحالة | المالك |
|---|---|---|---|---|---|---|
| Router | procedure/route | مجال وظيفي | اختبار مناسب | مرجع API | موثق/ناقص | محدد |
| Service | خدمة أعمال | مجال وظيفي | unit/integration | workflow | موثق/ناقص | محدد |
| Schema | جدول/علاقة | بيانات | DB test أو مراجعة | data model | موثق/ناقص | محدد |
| Page | صفحة مستخدم | واجهة | component/E2E | user guide | موثق/ناقص | محدد |
| Integration | منصة خارجية | تكامل | integration test | operations/API | موثق/ناقص | محدد |
| Job | cron/queue | تشغيل | workflow/operational check | runbook | موثق/ناقص | محدد |

## 9. سياسة التغيير أثناء التنفيذ

- أي طلب جديد يضاف إلى سجل التغييرات ولا يغير ترتيب المراحل مباشرة.
- أي تغيير يوسع نطاق مرحلة جارية يحتاج موافقة صريحة.
- أي اكتشاف يخص إصلاح كود أو أمان يسجل منفصلًا ويُرفع للمستخدم قبل تنفيذه.
- لا تُستخدم كلمة "مكتمل" إلا بعد اجتياز بوابة المرحلة.
- كل مرحلة تنتج تقريرًا قصيرًا يوضح ما تم فحصه وما لم يتم فحصه وما يحتاج قرارًا.

## 10. معيار الإغلاق النهائي

يُعتبر مشروع التوثيق مكتملًا عندما:

1. يكون `docs/README.md` فهرسًا صحيحًا ومحدثًا.
2. تكون لكل مرحلة/مجال وثيقة مرجعية أو سبب موثق لعدم الحاجة إليها.
3. تكون الوثائق متطابقة مع الكود والاختبارات ومخطط البيانات الحالي.
4. تكون الوثائق القديمة مدمجة أو مؤرشفة أو موسومة ببديل واضح.
5. تكون مصفوفة التغطية بلا عناصر حرجة غير مصنفة.
6. تمر فحوص الروابط والتنسيق والجودة المناسبة.
7. تكون قواعد CI وPull Request قادرة على منع تراجع التوثيق.
8. تكون لكل وثيقة مرجعية حالة ومالك وتاريخ مراجعة ومصادر واضحة.
