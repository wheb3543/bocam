### 2.3 الفرضية التشغيلية

إذا بُنيت أدلة التشغيل من `package.json` و`check-env.mjs` وملفات Docker وملفات البيئة الفعلية، ثم جُربت الأوامر في بيئة آمنة، فسيصبح مسار التثبيت قابلًا لإعادة التنفيذ دون الاعتماد على تعليمات تاريخية أو أسرار مضمنة.

**التحقق المضاد:** أي أمر أو متغير أو خدمة لا يمكن تشغيله أو ربطه بملف مصدر فعلي سيُسجل `needs-verification` ولن يظهر كخطوة إلزامية.

## 3. نطاق المرحلة وحدودها

### داخل النطاق

- المتطلبات الرسمية للإصدارات والأدوات.
- تثبيت الحزم وتشغيل check/dev/build/start.
- مصفوفة متغيرات البيئة حسب البيئة والسرية والإلزامية.
- التهيئة المحلية وقواعد البيانات وRedis.
- Docker وCompose المحلي والإنتاجي كما هما في الملفات الفعلية.
- Drizzle generate/migrate/push/studio.
- وضع المحاكاة إذا أثبته الكود فعليًا.
- دليل استكشاف أخطاء التهيئة والتشغيل.
- تحديث `README.md` و`QUICK_START.md` و`docs/installation/INSTALLATION_GUIDE.md` والروابط التشغيلية اللازمة.

### خارج النطاق

- تغيير منطق `check-env.mjs` أو تعريف متغيرات جديدة دون قرار منفصل.
- إصلاح بنية Docker أو Compose نفسها.
- تنفيذ ترحيلات أو تهيئة قاعدة بيانات إنتاجية.
- توثيق تفاصيل الترخيص أو WhatsApp أو API خارج متطلبات البيئة العامة.
- كشف أو نسخ قيم ملفات `.env` الحقيقية.

## 4. خطة التنفيذ الدقيقة

### المهمة 2.1: تثبيت مصفوفة الأدوات والإصدارات

**الإجراء:** مطابقة Node وpnpm وMySQL/TiDB وRedis وDocker مع `package.json` و`Dockerfile` وAGENTS والوثائق.  
**الناتج:** جدول متطلبات رسمي مع مصدر كل إصدار.  
**معيار القبول:** لا تذكر الوثائق إصدارًا متعارضًا أو أمر مدير حزم غير معتمد.

### المهمة 2.2: حصر أوامر المشروع

**الإجراء:** تصنيف scripts إلى install، development، validation، database، seed، build، release، Docker، license.  
**الناتج:** مرجع أوامر مرتبط مباشرة بـ`package.json`.  
**معيار القبول:** كل أمر موثق موجود فعليًا، وكل أمر مهم غير موثق يضاف للمراجعة.

### المهمة 2.3: بناء مصفوفة متغيرات البيئة

**الإجراء:** استخراج المتغيرات من الكود وقوالب البيئة، وتصنيفها إلى required-at-startup وfeature-optional وbuild-time وdeployment-only وsecret.  
**الناتج:** جدول يضم الاسم والوصف والمصدر والبيئة والقيمة النموذجية الآمنة.  
**معيار القبول:** لا تُطبع قيمة سرية، ولا يوصف متغير بأنه مطلوب إلا إذا أثبته الإقلاع أو المسار المختص.

### المهمة 2.4: مطابقة `check-env`

**الإجراء:** ربط سلوك `scripts/check-env.mjs` بالمصفوفة، وتحديد الفرق بين الفحص الحالي ومتطلبات الميزات.  
**الناتج:** قسم واضح يشرح ما يفحصه السكربت وما لا يفحصه.  
**معيار القبول:** لا توحي الأدلة بأن نجاح `check-env` يثبت جاهزية كل التكاملات.

### المهمة 2.5: توثيق التثبيت المحلي

**الإجراء:** إعادة كتابة مسار local setup باستخدام pnpm وNode الحاليين و`.env.example` المناسب، ثم التحقق من الأوامر.  
**الناتج:** خطوات clone/install/env/db/dev قابلة للتنفيذ.  
**معيار القبول:** المسار لا يعتمد على Node 18 أو `npx` أو ملف غير موجود.

### المهمة 2.6: توثيق قواعد البيانات وDrizzle

**الإجراء:** فصل `db:push` و`db:generate` و`db:migrate` و`db:studio` وseed، وتوضيح متطلبات `DATABASE_URL`.  
**الناتج:** قسم تشغيل قاعدة البيانات مع تحذير الإنتاج.  
**معيار القبول:** لا تُوصف `db:push` كبديل آمن دائمًا لترحيلات الإنتاج دون توضيح.

### المهمة 2.7: توثيق Redis ووضع المحاكاة

**الإجراء:** التحقق من استخدام Redis وملفات mock الفعلية، وفصل ما هو موجود في الكود عن الأمثلة التاريخية في `MOCK_ENVIRONMENT_GUIDE.md`.  
**الناتج:** جدول optional/required وملاحظات حدود mock.  
**معيار القبول:** لا تعلن الأدلة محاكاة لخدمة لا يثبتها الكود الحالي.

### المهمة 2.8: توثيق Docker وCompose

**الإجراء:** مطابقة Dockerfile وCompose الجذري وCompose deploy وملفات env الخاصة بهما، وتحديد الخدمات والمنافذ والمجلدات والصحة.  
**الناتج:** مسار Docker development ومسار production منفصلان.  
**معيار القبول:** كل أمر Compose يشير إلى ملف موجود وخدمة موجودة، ولا تختلط أسرار الإنتاج بالأمثلة.

### المهمة 2.9: توثيق البناء والإصدار

**الإجراء:** توثيق مدخلي Vite، `pnpm build`، `release:client`، static serving، وruntime production.  
**الناتج:** مخطط build → dist → start.  
**معيار القبول:** ذكر `dist/index.js` و`dist/public` وhealth check بمصادرها.

### المهمة 2.10: توثيق استكشاف الأخطاء

**الإجراء:** إنشاء جدول للأخطاء الشائعة: متغيرات ناقصة، DB refused، Redis، منفذ 3000، build، migrations، Docker health.  
**الناتج:** خطوات تشخيص آمنة مع أوامر تحقق.  
**معيار القبول:** لا تحتوي الحلول على أوامر مدمرة أو حذف lockfile كحل افتراضي.

### المهمة 2.11: ربط المصفوفة والفهرس

**الإجراء:** تحديث مصفوفة التغطية وسجل الوثائق وروابط الفهرس بمراجع التشغيل الجديدة.  
**الناتج:** traceability بين scripts والوثائق والبيئات.  
**معيار القبول:** كل وثيقة تشغيل محدثة مرتبطة بمصدر كود أو إعداد فعلي.

### المهمة 2.12: التحقق وإغلاق المرحلة

**الإجراء:** تشغيل فحوص الوثائق والتنسيق وTypeScript، واختبار الأوامر الآمنة الممكنة، ثم إعداد تقرير إغلاق المرحلة.  
**الناتج:** تقرير نتائج ومصفوفة فجوات محدثة.  
**معيار القبول:** اجتياز قائمة القبول وتسجيل ما تعذر اختباره بسبب أسرار أو خدمات خارجية.

## 5. معايير الجودة

- كل إصدار أو أمر أو مسار ملف مرتبط بمصدر فعلي.
- فصل التطوير عن الاختبار والإنتاج.
- لا أسرار أو رموز وصول أو بيانات إنتاج في الوثائق.
- أمثلة `.env` تستخدم قيمًا وهمية واضحة.
- لا تستخدم الوثائق أوامر `sudo` أو حذف ملفات كحل افتراضي دون تحذير ونطاق.
- توضيح أن `check-env` فحص أولي وليس اختبار تكامل شامل.
- توضيح متطلبات الصحة والجاهزية ومتى تكون Redis أو التكاملات الخارجية مطلوبة.
- عدم تعديل الكود أو ملفات البيئة الحقيقية ضمن تحديث التوثيق.
