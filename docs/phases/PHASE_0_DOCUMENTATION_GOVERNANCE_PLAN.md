# خطة المرحلة 0: تأسيس حوكمة التوثيق ومصفوفة التغطية

**الحالة:** مكتملة بعد التنفيذ والمراجعة  
**التاريخ:** 2026-09-11  
**المرحلة الرئيسية:** 0 من 19  
**المنهجية:** Phase-Gate Methodology  
**نطاق المرحلة:** حوكمة التوثيق والفهرسة والمصفوفة فقط

## 1. هدف المرحلة

إنشاء الأساس التنظيمي الذي ستعتمد عليه جميع مراحل تحديث وثائق المشروع لاحقًا، دون إعادة كتابة وثائق المجالات أو نقلها قبل إنشاء سجل واضح يحدد:

- ما هي الوثائق الموجودة فعلًا.
- ما المجال الذي تنتمي إليه كل وثيقة.
- ما حالة كل وثيقة.
- ما ملفات الكود والاختبارات التي تغطيها.
- ما الوثيقة المرجعية عند وجود تكرار.
- ما النواقص والتعارضات والقرارات التي تحتاج اعتمادًا.

| F0-08 | توجد وثائق حوكمة سابقة وتقارير جرد وخطط تنفيذ قد تتداخل | يجب تحديد المرجع قبل الدمج أو الأرشفة |

### 2.3 الفرضية التشغيلية

إذا تم إنشاء سجل مركزي مولد من الملفات الفعلية، مع قاموس حالات ومجالات وقواعد روابط، فستصبح المراحل اللاحقة قابلة للقياس ويمكن كشف الوثائق اليتيمة والتكرار قبل تعديل محتوى المجالات.

**التحقق المضاد:** إذا تعذر ربط الملفات بالمجال أو المصدر البرمجي دون مراجعة يدوية، فسيتم تسجيلها كـ `unclassified` ولن تُخفى تحت تصنيف تخميني.

## 3. نطاق المرحلة وحدودها

### داخل النطاق

- فهرس الوثائق الرئيسي.
- سجل الوثائق والمجالات والحالات.
- قالب بيانات الوثيقة.
- مصفوفة التغطية الأولية.
- سجل التعارضات والنواقص والقرارات.
- قواعد التسمية والروابط والملكية والمراجعة.
- تحديث سياسة التوثيق وقواعد CI اللازمة لهذه الحوكمة.

### خارج النطاق

- إعادة كتابة وثائق المصادقة أو WhatsApp أو CMS أو أي مجال آخر.
- تعديل منطق التطبيق أو قاعدة البيانات أو الاختبارات الوظيفية.
- نقل جماعي أو حذف أو إعادة تسمية الوثائق.
- اعتماد محتوى تجاري أو قانوني غير مؤكد.
- إنشاء توثيق تفصيلي للـ API أو الجداول قبل مرحلة مجاله.

## 4. خطة التنفيذ الدقيقة

### المهمة 0.1: تثبيت خط أساس المستودع

**الإجراء:** تسجيل حالة الملفات الحالية، عدد الوثائق، الملفات المستثناة، والملفات الجديدة الخاصة بالخطة والجرد.  
**المدخلات:** `find` أو أداة جرد قابلة للتكرار، Git status، بنية المستودع.  
**الناتج:** سجل خط أساس مؤرخ.  
**معيار القبول:** يمكن إعادة تشغيل أمر الجرد والحصول على نتيجة متسقة، مع تفسير أي فرق.

### المهمة 0.2: تعريف قاموس المجالات

**الإجراء:** إنشاء قائمة المجالات المعتمدة المتوافقة مع الخطة العامة: Overview، Getting Started، Authentication/RBAC، Security/Licensing، Data، API، Appointments، Patients، Campaigns/Leads، Offers/Camps/Doctors، Tasks/Teams/Notifications، WhatsApp، Social Integrations، CMS/Media، Analytics/Tracking، Frontend/PWA/Accessibility، Testing/Quality، Operations.  
**الناتج:** معرف مجال ثابت ووصف وحدود لكل مجال.  
**معيار القبول:** لا توجد وثيقة مصنفة تحت مجال غير موجود في القاموس؛ والوثائق غير الواضحة تحمل `unclassified` بدل التخمين.

### المهمة 0.3: تعريف قاموس الحالات

**الإجراء:** اعتماد الحالات التالية:

| الحالة | الاستخدام |
|---|---|
| `canonical` | المرجع الحالي المعتمد للموضوع |
| `working` | وثيقة قيد التطوير أو المراجعة |
| `deprecated` | وثيقة لم تعد مرجعًا ويجب توجيه القارئ لبديل |
| `archived` | وثيقة تاريخية محفوظة للرجوع فقط |
| `generated` | مخرجات مولدة لا تعدل يدويًا كمصدر أساسي |
| `unclassified` | لم تُراجع بعد أو تعذر تحديد وضعها |

**معيار القبول:** لكل حالة تعريف وقاعدة انتقال وبديل أو سبب واضح عند عدم وجود بديل.

### المهمة 0.4: تصميم سجل الوثائق

**الإجراء:** تصميم سجل قابل للتحديث، ويفضل أن يكون Markdown/JSON أو مصدرًا واضحًا يمكن توليده، بالحقول التالية:

```text
path
title
language
domain
document_type
status
audience
owner
source_code_paths
test_paths
related_documents
supersedes
last_reviewed
review_due
evidence_level
notes
```

**معيار القبول:** كل حقل له تعريف وقيم مسموحة وقاعدة تعبئة، ولا يعتمد السجل على أسماء الملفات وحدها.

### المهمة 0.5: بناء مصفوفة التغطية الأولية

**الإجراء:** ربط عناصر الكود والاختبارات والوثائق على مستوى المجلد أو الوحدة في البداية، ثم ترك التفاصيل الدقيقة للمجال المختص.  
**العلاقات المطلوبة:** `code → tests → docs → owner → status`.  
**معيار القبول:** كل router رئيسي، service رئيسية، schema رئيسي، صفحة رئيسية، integration، وjob له صف أو سبب استثناء.

### المهمة 0.6: تصنيف الوثائق الموجودة

**الإجراء:** تصنيف كل وثيقة في النطاق إلى مجال ونوع وحالة وجمهور، مع عدم تعديل محتوى الوثيقة إلا لإضافة metadata معتمدة.  
**أنواع الوثائق:** overview، guide، reference، architecture، policy، report، plan، research، runbook، changelog، archive.  
**معيار القبول:** لا توجد وثيقة صامتة في السجل؛ الوثائق غير المفهومة تسجل `unclassified` مع ملاحظة.

### المهمة 0.7: تحديد الوثائق المرجعية والتكرار

**الإجراء:** مقارنة العناوين والمحتوى والروابط والموضوعات لتحديد المرشح المرجعي لكل موضوع، دون دمج أو حذف.  
**الناتج:** سجل تعارضات يوضح `canonical_candidate` و`duplicates` و`decision_required`.  
**معيار القبول:** كل مجموعة متكررة لها قرار مؤجل واضح أو مرجع مؤقت واضح.

### المهمة 0.8: تحديث فهرس الوثائق

**الإجراء:** إعادة بناء `docs/README.md` ليعرض الروابط الفعلية والتصنيف المعتمد، مع فصل أدلة المستخدم والمراجع والتقارير والأرشيف.  
**معيار القبول:** لا يذكر الفهرس ملفًا غير موجود، وكل وثيقة `canonical` قابلة للوصول من الفهرس أو من فهرس مجالها.

### المهمة 0.9: تحديث سياسة التوثيق

**الإجراء:** تحديث `docs/introduction/DOCUMENTATION_POLICY.md` لتضمين سجل الوثائق، metadata، حالات الوثيقة، الملكية، التحديث المرتبط بالتغييرات، وقواعد عدم كشف الأسرار.  
**معيار القبول:** السياسة متوافقة مع الواقع ولا تفرض توثيقًا آليًا لكل سطر دون تمييز؛ تفرق بين التوثيق العام، التعليقات الداخلية، والمرجع التشغيلي.

### المهمة 0.10: وضع قواعد التسمية والروابط

**الإجراء:** توثيق قواعد أسماء الملفات، العناوين، اللغة، الروابط النسبية، أسماء المجالات، وتاريخ التقارير.  
**معيار القبول:** توجد أمثلة صحيحة وخاطئة، وقاعدة واضحة للوثائق القديمة والمستبدلة.

### المهمة 0.11: إضافة التحقق الآلي المناسب

**الإجراء:** تقييم فحص Markdown الحالي وإضافة أقل قدر ضروري من التحقق: الروابط، الملفات المشار إليها، صحة سجل الوثائق، وتنسيق السجل.  
**معيار القبول:** يفشل التحقق عند رابط داخلي غير موجود أو مسار سجل غير موجود، ولا يفشل بسبب روابط خارجية مستثناة وفق سياسة واضحة.

### المهمة 0.12: مراجعة بوابة المرحلة

**الإجراء:** تشغيل فحوص المرحلة ومراجعة diff مقابل هذه الخطة، ثم إعداد تقرير إغلاق المرحلة.  
**معيار القبول:** اكتمال قائمة القبول في القسم 7، وتسجيل كل استثناء أو قرار مؤجل.

## 5. معايير الجودة الإلزامية

### 5.1 معايير المحتوى

- لا ادعاء بلا مصدر من الكود أو الاختبار أو قرار معتمد.
- لا تكرار لوصف واحد في وثيقتين مرجعيتين.
- كل وثيقة قديمة لها حالة وبديل أو سبب أرشفة.
- كل مثال حساس يخلو من الأسرار والبيانات الشخصية.
- اللغة والأسلوب ثابتان داخل الوثيقة، مع إبقاء أسماء الكود كما هي.

### 5.2 معايير البنية

- العنوان يصف الغرض لا اسم المهمة فقط.
- كل وثيقة تبدأ ببيانات الحالة والمجال والجمهور والمراجعة.
- الروابط نسبية وقابلة للفحص.
- القوائم التي يمكن توليدها لا تكتب يدويًا إذا كان ذلك يسبب تقادمًا.
- لا تستخدم أسماء مثل `final` أو `new` أو `latest` كبديل للحالة.

### 5.3 معايير الكود والأتمتة

- أدوات الجرد قابلة لإعادة التشغيل ولا تكشف أسرار البيئة.
- أي script جديد يلتزم TypeScript/Node conventions الموجودة.
- لا يتم إدخال اعتماد جديد قبل إثبات الحاجة إليه.
- التحقق الآلي يستخدم أوامر المشروع الحالية متى أمكن.
- لا يتم تعديل منطق التطبيق ضمن هذه المرحلة.

## 7. قائمة قبول المرحلة

لا تعتبر المرحلة 0 مكتملة إلا عند تحقق ما يلي:

- [ ] سجل خط الأساس محفوظ ومؤرخ.
- [ ] قاموس المجالات معتمد ومستخدم.
- [ ] قاموس الحالات وقواعد انتقالها موثقة.
- [ ] سجل الوثائق منشأ وقابل للتحديث.
- [ ] مصفوفة التغطية الأولية منشأة.
- [ ] كل وثيقة في النطاق لها سجل أو حالة `unclassified` مبررة.
- [ ] مجموعات التكرار والتعارضات مسجلة دون حذف.
- [ ] `docs/README.md` لا يحتوي روابط محلية معروفة مكسورة.
- [ ] سياسة التوثيق محدثة ومتوافقة مع آلية السجل.
- [ ] قواعد الأسماء والروابط والـ metadata موثقة.
- [ ] التحقق الآلي المناسب يعمل على الملفات المعدلة.
- [ ] لا يوجد تعديل كود خارج نطاق الحوكمة والأتمتة المعتمدة.
- [ ] تقرير إغلاق المرحلة يذكر ما تم وما لم يتم وما يحتاج قرارًا.
- [ ] تم طلب واعتماد الانتقال إلى المرحلة 1 كتابة.

## 8. فحوص التحقق المقترحة

سيتم اختيار الأوامر النهائية بعد فحص بيئة المشروع، لكن الحد الأدنى هو:

```bash
pnpm format:check
pnpm check
```

إضافة إلى فحص الروابط المحلي وسجل الوثائق. إذا لم يكن تشغيل `pnpm check` ضروريًا لتغيير Markdown فقط، يسجل السبب ويستخدم أضيق تحقق مناسب بدل تشغيل شامل غير مفيد.

## 9. بوابة التوقف الحالية

**هذه الوثيقة هي خطة المرحلة 0 التفصيلية وليست تنفيذًا للمرحلة.**  
بعد اعتمادك لهذه الخطة، يمكن تنفيذ المهام من `0.1` إلى `0.12` بالتتابع، مع مراجعة داخلية بعد كل مجموعة صغيرة، ثم التوقف عند نهاية المرحلة لتقديم تقرير الإغلاق وطلب إذن المرحلة 1.

**المطلوب الآن:** اعتماد خطة المرحلة 0 بعبارة صريحة مثل: `نعم، ابدأ تنفيذ المرحلة 0`.
