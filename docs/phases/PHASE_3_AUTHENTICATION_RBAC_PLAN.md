### 2.2 النتائج المثبتة

| الرمز | النتيجة | الأثر التوثيقي |
|---|---|---|
| F3-01 | مسار المصادقة المحلية يعتمد Cookie باسم `admin_session` وJWT موقّع بـ`JWT_SECRET` ثم يعيد تحميل المستخدم من قاعدة البيانات ويتحقق من `isActive` | يجب توثيق التحقق من الجلسة وعدم الاكتفاء ببيانات JWT |
| F3-02 | مسار OAuth يستخدم `/api/oauth/callback`، ويتحقق من `code/state` ثم يسمح بالبريد المعتمد أو ينشئ Access Request | يجب توثيق تدفق allowed/unauthorized/access-request |
| F3-03 | `context.ts` يجرب الجلسة المحلية أولًا ثم يسقط إلى `sdk.authenticateRequest` لجلسة OAuth | يجب توضيح أولوية المسارين وحدود كل جلسة |
| F3-04 | جلسة OAuth في `sdk.ts` تستخدم `ENV.cookieSecret` وHS256 وبيانات openId/appId/name، بينما المحلي يستخدم `JWT_SECRET` وبيانات userId/username/role/type | يجب تسجيل فرق أسرار الجلسات وبنيتها كحقيقة معمارية |
| F3-05 | خصائص الكوكي تختلف: OAuth يستعمل `getSessionCookieOptions` مع `sameSite: none` وsecure حسب الطلب، والمحلي يضبط `sameSite: lax` وsecure في production | يجب توثيق السلوك والفجوة دون توحيدها في هذه المرحلة |
| F3-06 | `protectedProcedure` يتحقق من وجود المستخدم، و`adminProcedure` يتحقق من `ctx.user.role === admin`، و`permissionProcedure` يتحقق من صلاحية دقيقة | يجب فصل authentication عن authorization وعن feature licensing |
| F3-07 | `hasRolePermission` يمنح admin كل الصلاحيات، ثم يبحث عن assignment نشط، ثم دور النظام، ثم fallback لتعريف الدور الافتراضي | يجب توثيق ترتيب القرار وتوافق legacy |
| F3-08 | `doesRolePermissionSetGrant` يدعم صلاحيات الإدارة القديمة مثل `users.manage` كبديل لبعض الصلاحيات التفصيلية | يجب وسم هذا كطبقة توافق انتقالية لا كمنح شامل جديد |
| F3-09 | `shared/rolePermissions.ts` يحتوي أدوارًا أساسية ومجموعات وصلاحيات وتسميات وتعريفات افتراضية | يجب إنشاء مرجع Role × Permission قابل للتتبع |
| F3-10 | `auth.permissions` يعيد صلاحيات المستخدم من `ROLE_PERMISSIONS`، مع حماية `protectedProcedure` | يجب توثيق مصدر الصلاحيات الذي يستهلكه العميل |
| F3-11 | `ProtectedRoute` يحمي الميزات بناءً على الترخيص، وليس بالضرورة بناءً على جلسة المستخدم أو RBAC | يجب عدم الخلط بين feature gate وpermission gate |
| F3-12 | `auth.updateProfile` معرف كـ`publicProcedure` لكنه يفحص `ctx.user` يدويًا، بينما `register` يستخدم `adminProcedure` | يجب تسجيل نمط الحماية غير المتجانس كفجوة مراجعة، دون إصلاح كود الآن |
| F3-13 | اختبارات auth الحالية تركز على bcrypt وJWT منفصلين، بينما اختبارات RBAC تغطي workflows وقرارات access requests | يجب تمييز ما تثبته الاختبارات وما لا تثبته |

### 2.3 الفرضية التشغيلية

إذا وُثقت مسارات المصادقة والجلسات والصلاحيات من الملفات الفعلية، ثم رُبطت كل حماية بإجراء أو اختبار، فسيصبح من الممكن التمييز بين هوية المستخدم، وصلاحية الإجراء، وصلاحية الميزة المرخصة، وكشف الفجوات دون تخمين.

**التحقق المضاد:** أي قرار وصول لا يمكن ربطه بـmiddleware أو procedure أو feature gate أو اختبار سيُسجل كـ`needs-verification` أو `gap`، ولن يُعلن كضابط أمني موجود.

## 3. نطاق المرحلة وحدودها

### داخل النطاق

- المصادقة المحلية username/password.
- OAuth/Manus callback وsession SDK.
- إنشاء الجلسة والتحقق منها وانتهائها.
- خصائص Cookie وJWT وsession payloads.
- `publicProcedure` و`protectedProcedure` و`adminProcedure` و`permissionProcedure`.
- الأدوار الأساسية والصلاحيات التفصيلية وlegacy compatibility.
- Access Requests والقبول والرفض وهوية صاحب القرار.
- حواجز ProtectedRoute وfeature licensing كطبقة منفصلة.
- تحديث وثائق الأمان وRBAC والمساهمة ومصفوفة التغطية.

### خارج النطاق

- تغيير خوارزمية أو سر جلسة أو خصائص Cookie.
- إعادة تصميم RBAC أو نقل الصلاحيات.
- إصلاح `auth.updateProfile` أو أي عدم تجانس برمجي.
- توثيق الترخيص العتادي بالتفصيل؛ يراجع في المرحلة 4.
- توثيق كل صلاحية لكل router بالتفصيل؛ يستكمل مع مراحل المجالات.
- إدخال بيانات مستخدمين أو أسرار أو tokens حقيقية.

## 4. خطة التنفيذ الدقيقة

### المهمة 3.1: رسم مسارات المصادقة

**الإجراء:** إنشاء مخطط local login وOAuth callback وsession restoration وlogout وunauthorized access.  
**الناتج:** خريطة تدفق مع مصادر الملفات.  
**معيار القبول:** كل انتقال مرتبط بمصدر، وحالات الفشل موضحة.

### المهمة 3.2: توثيق الجلسات والكوكيز

**الإجراء:** توثيق اسم الكوكي، payload، السر، الخوارزمية، المدة، httpOnly، secure، sameSite، ومسار التحقق لكل مسار.  
**الناتج:** مرجع جلسات لا يكشف القيم السرية.  
**معيار القبول:** يظهر الفرق بين local JWT وOAuth SDK session دون تقديم أحدهما كبديل للآخر.

### المهمة 3.3: توثيق OAuth وAccess Request

**الإجراء:** شرح code/state exchange، user info، فحص allowed email، إنشاء الطلب، redirect، وتسجيل آخر دخول.  
**الناتج:** دليل OAuth وAccess Request.  
**معيار القبول:** القبول والرفض والبريد المفقود والفشل الخارجي موثقة.

### المهمة 3.4: توثيق middleware والحماية الخلفية

**الإجراء:** فصل public/protected/admin/permission procedures وتوثيق ما يحدث عند غياب المستخدم أو الصلاحية.  
**الناتج:** مرجع enforcement للخادم.  
**معيار القبول:** كل نوع حماية مرتبط بالملف والمخرجات المتوقعة.

### المهمة 3.5: بناء مصفوفة الأدوار والصلاحيات

**الإجراء:** استخراج الأدوار الأساسية ومجموعات الصلاحيات والتعريفات الافتراضية والتسميات.  
**الناتج:** Role × Permission matrix، مع تمييز system/custom/legacy.  
**معيار القبول:** لا تُختصر صلاحيات admin أو legacy في وصف مضلل.

### المهمة 3.6: توثيق ترتيب قرار الصلاحية

**الإجراء:** توثيق admin bypass، assignment النشط، system role، fallback default، وlegacy management mapping.  
**الناتج:** خوارزمية قرار قابلة للمراجعة.  
**معيار القبول:** حالات عدم وجود assignment أو role غير صالح موضحة.

### المهمة 3.7: توثيق ProtectedRoute وFeature Gate

**الإجراء:** فصل `ProtectedRoute` المعتمد على license feature عن RBAC، وتوثيق loading والredirect وfallback.  
**الناتج:** مرجع حواجز الواجهة.  
**معيار القبول:** لا يقال إن feature gate يثبت أن المستخدم يملك صلاحية RBAC.

### المهمة 3.8: مطابقة الاختبارات

**الإجراء:** ربط كل سلوك موثق باختبار موجود، وتحديد فجوات الاختبار في الجلسات والكوكيز وOAuth والحماية.  
**الناتج:** جدول behavior → test → documentation.  
**معيار القبول:** لا تُنسب حماية إلى اختبار لا يغطيها فعليًا.

### المهمة 3.9: تحديث وثائق الأمان وRBAC

**الإجراء:** تحديث `docs/introduction/SECURITY.md` و`SECURITY.md` ووثائق RBAC ذات الصلة، وإنشاء مرجع هوية وصلاحيات عند الحاجة.  
**الناتج:** وثائق مرجعية متوافقة مع التنفيذ الحالي.  
**معيار القبول:** الأسرار والتفاصيل الحساسة غير مكشوفة، والفجوات مسجلة بوضوح.

### المهمة 3.10: تحديث مصفوفة التغطية وسجل التعارضات

**الإجراء:** ربط ملفات auth/RBAC/tests بالوثائق وتسجيل اختلافات Cookie وpublicProcedure وlegacy fallback.  
**الناتج:** traceability وقرارات مؤجلة واضحة.  
**معيار القبول:** كل فجوة لها رمز ومالك وحالة.

### المهمة 3.11: التحقق وإغلاق المرحلة

**الإجراء:** تشغيل الاختبارات المركزة و`pnpm check` و`pnpm docs:check` وPrettier وفحص الروابط، ثم إعداد تقرير الإغلاق.  
**الناتج:** تقرير نتائج وبوابة المرحلة 4.  
**معيار القبول:** اجتياز قائمة القبول وتوثيق الاختبارات التي تعذر تشغيلها.

## 5. معايير الجودة

- فصل المصادقة Authentication عن التفويض Authorization وعن الترخيص Licensing.
- عدم نشر JWT secrets أو cookie secrets أو tokens أو بيانات مستخدمين.
- توثيق حالات الرفض والنجاح وانتهاء الجلسة، لا المسار الناجح فقط.
- كل صلاحية في المصفوفة مرتبطة بتعريف مصدرها.
- تمييز صلاحيات admin الشاملة والتوافق legacy عن الصلاحيات العادية.
- عدم اعتبار وجود `ProtectedRoute` دليلًا على حماية API المقابلة.
- عدم اعتبار نجاح اختبار JWT المنفصل دليلًا على سلامة تدفق الجلسة الكامل.
- عدم تعديل سلوك المصادقة أو الصلاحيات ضمن تحديث الوثائق.
